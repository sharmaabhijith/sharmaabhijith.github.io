Research

Does the agent actually follow its rules?

Capability benchmarks ask what an agent can do. Safety red-teaming asks whether it says something harmful. I work on the question in between: whether a deployed agent complies with the policies it was given, across many turns, hidden tool calls and downstream state.

the short version: I build auditors

Policy violations are hard to see. They emerge after several benign turns, hide inside tool calls the user never sees, and surface only in the state of some downstream system. A static test suite covers a few of them. A human red-teamer finds more, slowly. Neither scales to the number of agents being deployed.

My PhD at MBZUAI, advised by Salem Lahlou and Nils Lukas, is about building auditors for that gap: learned agents that interact with a target system the way a real user would and search efficiently for the places where it breaks its rules. I care about coverage over raw hit counts, about auditors that stay plausible, and about verification that holds up when the target is far larger than the auditor.

Before this I spent four years on the physical side of robustness: adversarial patches on vision models, defenses that survive more than one patch, and a real-time testing framework for autonomous-vehicle perception that we validated outdoors. It is the same question at a different layer of the stack. How do you find the failure before deployment does?

Threads

four, loosely coupled
01 · active

Learning to audit

PROBE (Policy Rule Observation via Behavioral Exploration) frames auditing as a partially observed Markov game between an auditor and a target agent with private tools and state. The auditor is trained with RL against severity-weighted verifiers, rewarded for distinct violations, progress into tool-relevant states, novelty and plausibility. A 4B auditor trained this way covers more policies and finds more violations than a zero-shot 30B adversary.

02 · active

Fuzz verification of multi-agent systems

Treating a multi-agent system the way a fuzzer treats a program: generate inputs that push it into rarely visited states, watch for invariants that break, and learn where to look next. The interesting failures are the ones no single agent causes on its own: they appear when agents, tools and memories interact.

in progress
03 · active

Diversity-seeking exploration

Finding one failure is easy. Finding all the different ones is the hard part. GFlowNets sample in proportion to reward, which makes them a natural fit for generating diverse test cases and auditor behaviours. Work here includes loss-guided auxiliary agents that counter mode collapse, GFlowNet-finetuned LLM agents for diverse symbolic music (Flowphony), and graph environments contributed to torchgfn.

04 · 2021 – 2025

Robustness, privacy and physical-world testing

AVATAR evaluates autonomous-vehicle perception against adversarial patches in real time, in CARLA and outdoors, with a KDE-based detector for adversarial vehicles. Earlier work covered multi-patch attacks, naturalistic support artifacts that raise model confidence, image resurfacing as a model-agnostic defense, a survey of 100+ patch attacks and defenses, and a membership-inference analysis of spiking neural networks.
